# 合同管理 AI 原生应用技术架构设计文档

## 1. 文档目标

本文档用于指导基于当前合同管理本体模型，生成并落地一个“本体模型驱动 + AI 大模型驱动”的 AI 原生应用系统。

该文档的目标不是描述某个单点功能，而是定义一套完整、可生成、可运行、可扩展的技术架构，使后续 AI 大模型能够基于：

- 原始业务需求
- 合同管理本体模型 YAML
- 本技术架构文档
- UI 建模文档

共同生成完整的前后端应用程序，并支持后续持续演进。

---

## 2. 架构定位

### 2.1 系统本质

本系统是一个：

1. 以本体模型作为业务语义核心的模型驱动系统。
2. 以 AI 大模型作为生成引擎和运行时智能交互引擎的 AI 原生系统。
3. 采用 Hybrid UI 模式的企业级轻量应用。

### 2.2 核心设计理念

本系统不是“先写程序，再补 AI”，而是：

1. 先沉淀业务语义模型。
2. 再基于模型自动生成程序骨架、页面、接口、数据库映射与 AI 工具能力。
3. 最终让 AI 在运行时继续基于同一套语义模型进行对话式交互和能力编排。

这意味着本体模型在系统中承担三重角色：

1. 业务建模载体：表达对象、行为、规则、事件、场景、质量约束等业务语义。
2. 程序生成基础：供 AI 生成前端页面、后端 API、数据库结构和运行时注册表。
3. AI 推理知识底座：作为运行时 prompt/context 的结构化语义来源，提高 AI 对业务问题的理解精度和执行精度。

## 3. 总体架构

### 3.1 总体分层

整个系统采用单体应用、分层解耦的方式实现：

1. 本体模型层
2. 语义注册层
3. 后端服务层
4. AI 编排层
5. 前端 Hybrid UI 层
6. 数据存储层

### 3.2 分层说明

#### 3.2.1 本体模型层

来源于 `models/contract` 目录中的 YAML 文件，包括：

- `m1-object-model.yaml`
- `m2-behavior-model.yaml`
- `m3-rule-model.yaml`
- `m4-scenario-model.yaml`
- `m5-actor-model.yaml`
- `m6-compensation-model.yaml`
- `m7-quality-model.yaml`
- `me-event-model.yaml`
- `m9-contract-ui-model.yaml`

该层只表达语义，不直接承载运行逻辑。

#### 3.2.2 语义注册层

系统启动时首先解析全部本体模型 YAML，构建统一的运行时语义注册表 `Ontology Registry`。

该注册表是整个系统的运行时中枢，至少包含：

- 对象定义注册
- 属性定义注册
- 聚合边界注册
- 行为注册
- 规则注册
- 事件注册
- 用例注册
- 页面注册
- API 能力注册
- AI 工具能力注册

所有后端 API 暴露、前端页面绑定、AI 工具调用、动态 SQL 白名单控制，都基于该注册表实现。

#### 3.2.3 后端服务层

后端采用 `Python + Flask + sqlite3` 轻量化实现，不引入 SQLAlchemy。

后端职责包括：

- 提供业务 UI 所需 REST API
- 提供 AI 对话所需统一 API
- 暴露行为/查询/规则等可复用能力接口
- 执行本体模型驱动的校验、规则、查询和工具调用
- 向前端提供 SSE 流式响应

#### 3.2.4 AI 编排层

AI 编排层负责把运行时对话请求，路由到：

1. 已有 API 能力
2. 运行时工具函数
3. 只读动态 SQL 查询
4. 文本/表格/图表渲染协议

本层接入 `DeepSeek` 大模型，支持函数调用。

#### 3.2.5 前端 Hybrid UI 层

前端采用：

- `React`
- `TypeScript`
- `Vanilla CSS`
- `Lucide Icons` 或 `FontAwesome CDN`
- `ECharts`

前端由两类界面组成：

1. 固定功能界面：合同录入、开票录入、收款录入、合同查询等。
2. AI 动态界面：在对话区域动态渲染文本、表格、图表、操作建议等内容。

#### 3.2.6 数据存储层

数据库采用 `SQLite`。

SQLite 在当前阶段适合作为：

- 单体原型数据库
- 本地轻量部署数据库
- AI 原生应用 MVP 数据底座

## 4. Hybrid UI 架构

### 4.1 设计目标

系统采用 `Hybrid UI` 模式，而不是纯固定菜单式 UI，也不是纯聊天机器人式 UI。

核心原则：

1. 高频、确定性、结构化业务操作，提前提供固定 UI 页面。
2. 低频、探索式、分析式、临时性需求，交给 AI 对话区动态完成。
3. 无论是固定页面还是 AI 动态渲染，整体视觉风格必须统一。

### 4.2 固定业务 UI

本系统首批固定页面至少包括：

1. 合同录入页
2. 合同开票录入页
3. 合同收款录入页
4. 合同信息查询页

这些页面由 `m9-contract-ui-model.yaml` 驱动生成，使用多标签工作台模式呈现。

### 4.3 AI 动态 UI

AI 对话区支持以下渲染类型：

1. `text`
2. `table`
3. `chart`
4. `action`

说明如下：

- `text`：用于业务说明、状态反馈、执行结果说明。
- `table`：用于列表展示、统计结果、结构化查询结果。
- `chart`：用于趋势图、分布图、统计图，固定使用 `ECharts`。
- `action`：用于提示用户打开某个页面、查看详情、执行某个行为。

### 4.4 UI 一致性要求

固定页面与 AI 动态渲染必须统一以下风格元素：

- 统一色彩系统
- 统一边框与背景体系
- 统一表格风格
- 统一图表主题
- 统一文字和状态标签风格
- 统一交互术语

也就是说，AI 对话框里渲染的表格与主工作台中的查询表格，应被视为同一设计系统下的不同承载容器。

## 6. 运行时语义注册表 Ontology Registry

### 6.1 定位

`Ontology Registry` 是运行时的统一语义注册中心。

系统启动时加载全部 YAML，并生成内存结构，供以下模块统一使用：

- Flask API 层
- AI 编排层
- 前端元数据接口
- 动态 SQL 白名单控制器

### 6.2 注册表建议结构

建议注册表包含如下字典或索引：

```python
registry = {
    "aggregates": {},
    "entities": {},
    "behaviors": {},
    "rules": {},
    "events": {},
    "use_cases": {},
    "quality_annotations": {},
    "pages": {},
    "navigation": {},
    "api_capabilities": {},
    "ai_tools": {},
    "db_whitelist": {}
}
```

### 6.3 注册表用途

#### API 能力注册

把 `M2` 中可执行行为、查询行为注册成统一 API 能力。

#### AI 工具注册

把可安全复用的行为、查询、规则、报表能力注册成函数调用工具。

#### 页面元数据注册

把 `m9-contract-ui-model.yaml` 注册成页面元数据，供前端动态生成页面骨架。

#### 数据库白名单注册

根据 `M1` 和查询行为，生成只读 SQL 可访问的表名、字段名、关联关系白名单。

## 7. 后端技术架构

### 7.1 技术选型

- Web 框架：`Flask`
- 数据访问：`sqlite3`
- 流式输出：`SSE`
- 配置管理：基于 `YAML + 环境变量`
- 模型解析：YAML 解析器
- AI 调用：DeepSeek API

### 7.2 后端模块划分

建议后端至少划分为以下模块：

1. `app.py` 或 `main.py`
2. `config/`
3. `ontology/`
4. `api/`
5. `services/`
6. `repositories/`
7. `ai/`
8. `sql_readonly/`
9. `sse/`
10. `utils/`

### 7.3 模块职责

#### `ontology/`

负责：

- 加载 YAML
- 校验 YAML
- 构建注册表
- 输出运行时元数据

#### `api/`

负责：

- 暴露 REST 接口
- 参数接收与返回
- 统一错误响应

#### `services/`

负责：

- 行为执行
- 查询执行
- 规则执行
- 事件后处理

#### `repositories/`

负责：

- 使用 `sqlite3` 访问数据库
- 执行结构化查询
- 执行增删改查

#### `ai/`

负责：

- DeepSeek 对接
- prompt 构建
- tool schema 注册
- function calling 调用处理
- 输出渲染协议转换

#### `sql_readonly/`

负责：

- 动态 SQL 只读编排
- SQL 白名单校验
- 禁止 CUD/DDL
- 查询结果限制

#### `sse/`

负责：

- AI 流式输出
- 事件分片推送
- 最终结构化消息收口

## 8. API 架构设计

### 8.1 API 设计原则

本系统后端必须保留统一 API 能力，这些 API 既服务固定页面，也服务 AI 对话。

原则如下：

1. 所有前端固定页面均通过 API 调用后端能力。
2. AI 对话优先复用已有 API。
3. 本体模型中的对象行为、规则、查询应尽量暴露为标准化能力接口。
4. 同一能力不应同时维护多套实现逻辑。

### 8.2 API 分类

建议分为以下五类接口：

#### 8.2.1 元数据接口

示例：

- `/api/meta/navigation`
- `/api/meta/pages`
- `/api/meta/ontology-summary`

用于向前端返回：

- 导航树
- 页面定义
- 字段与表单元数据

#### 8.2.2 行为接口

示例：

- `/api/behaviors/Contract_Create/execute`
- `/api/behaviors/Invoice_Create/execute`
- `/api/behaviors/Payment_Receive/execute`

这些接口直接对应 `M2` 中的写行为。

#### 8.2.3 查询接口

示例：

- `/api/queries/Contract_Query/execute`
- `/api/queries/Contract_GetDetail/execute`

这些接口对应 `M2` 中的查询行为。

#### 8.2.4 AI 接口

示例：

- `/api/ai/chat`
- `/api/ai/chat/stream`
- `/api/ai/tools`

用于承载 AI 对话、工具调用和流式输出。

#### 8.2.5 系统接口

示例：

- `/api/auth/login`
- `/api/auth/logout`
- `/api/health`

### 8.3 统一响应格式

建议全部 API 采用统一结构：

```json
{
  "success": true,
  "message": "ok",
  "data": {},
  "errorCode": null,
  "traceId": "..."
}
```

SSE 则采用事件流形式输出分段消息。

## 9. AI 编排架构

### 9.1 AI 能力定位

AI 在本系统中承担四类职责：

1. 业务问答
2. 功能导航
3. 工具调用
4. 动态查询与可视化展示

### 9.2 模型供应商

运行时大模型固定采用 `DeepSeek`。

API Key、Base URL、模型名通过独立配置文件提供，不硬编码在程序中。

### 9.3 函数调用模式

系统必须支持 `Function Calling`。

AI 在接收用户问题后，优先做能力决策：

1. 是否已有行为 API 可用
2. 是否已有查询 API 可用
3. 是否已有规则能力可用
4. 是否可使用只读 SQL 查询
5. 若都不可用，则退化为语义解释型回答

### 9.4 AI 工具分类

建议定义以下工具类别：

#### 页面导航工具

例如：

- 打开合同录入页
- 打开合同查询页

#### 查询工具

例如：

- 执行合同模糊查询
- 获取合同详情

#### 行为工具

例如：

- 执行合同录入
- 执行开票录入
- 执行收款确认

#### 图表生成工具

例如：

- 将查询结果转换为柱状图
- 将统计结果转换为折线图

#### SQL 只读工具

用于在缺少现成 API 能力时，动态生成并执行严格只读查询。

### 9.5 AI 决策顺序

运行时建议采用以下优先级：

1. 固定工具/API
2. 语义注册表已有查询能力
3. 只读动态 SQL
4. 纯文本解释

也就是：

- 能调用 API 就不直接拼 SQL
- 能调用标准查询就不走自由查询
- 不能写数据时必须明确提示没有 CUD 权限

## 10. 动态 SQL 只读方案

### 10.1 适用场景

当 AI 对话遇到以下情况时，可以启用动态 SQL：

1. 当前没有对应 API 能力
2. 用户请求是数据读取类问题
3. 问题可通过数据库直接查询回答

例如：

- “最近 30 天哪个客户合同金额最高？”
- “统计各部门合同金额分布”
- “按产品类型统计已开票金额”

### 10.2 严格边界

动态 SQL 必须严格只读。

禁止以下语句：

- `INSERT`
- `UPDATE`
- `DELETE`
- `REPLACE`
- `DROP`
- `ALTER`
- `TRUNCATE`
- `CREATE`
- `ATTACH`
- `PRAGMA` 写操作

如果 AI 判断用户请求需要写数据，必须明确回复：

> 当前 AI 对话能力仅支持只读查询，不具备新增、修改、删除权限。请通过系统固定业务页面执行对应操作。

### 10.3 安全控制

动态 SQL 模块至少要做以下限制：

1. 仅允许 `SELECT`
2. 仅允许访问白名单表
3. 仅允许访问白名单字段
4. 强制追加 `LIMIT`
5. 设置 SQL 执行超时
6. 禁止多语句执行
7. 记录审计日志
8. 对 SQL 进行关键字与结构校验

### 10.4 SQL 白名单来源

SQL 白名单不手工维护，而是从以下来源自动生成：

1. `M1` 对象模型
2. 已登记的查询行为
3. 预定义视图或统计口径

### 10.5 动态 SQL 执行链路

建议执行流程：

1. 用户发起自然语言问题
2. AI 判断当前无可复用 API
3. AI 请求 `readonly_sql_query` 工具
4. 后端根据注册表校验目标表和字段是否合法
5. 执行只读 SQL
6. 把结果转成 `text/table/chart`
7. 通过 SSE 返回前端

## 11. 数据库架构

### 11.1 数据库选型

数据库固定使用 `SQLite`。

适用原因：

1. 部署简单
2. 原型开发快
3. 单体应用足够轻量
4. 便于 AI 生成应用时快速落地

### 11.2 建表来源

数据库结构主要由 `M1` 对象模型映射生成。

建议映射策略：

- 合同聚合根映射为合同主表
- 付款条款映射为合同付款条款表
- 开票聚合根映射为开票主表
- 开票付款阶段映射为开票阶段映射表
- 产品、客户、部门、人员映射为主数据表

### 11.3 建议表

建议至少包含：

1. `contracts`
2. `contract_payment_terms`
3. `invoices`
4. `invoice_term_mappings`
5. `products`
6. `customers`
7. `departments`
8. `employees`
9. `users`
10. `chat_sessions`
11. `chat_messages`
12. `audit_logs`

### 11.4 登录用户表

由于当前不实现完整 RBAC，但需要登录，因此保留轻量登录表：

- 用户名
- 密码哈希
- 是否启用
- 显示名称

默认提供一个具备全部功能权限的管理员账号即可。

## 12. 登录与权限策略

### 12.1 当前阶段策略

当前阶段要求：

1. 系统必须支持登录。
2. 默认提供一个拥有全部功能权限的账号。
3. 暂不实现完整 RBAC。

### 12.2 与本体模型的关系

`M5` 主体模型保留，但当前主要作为：

- 语义占位
- 后续扩展基础
- 页面和能力边界说明

在当前 MVP 阶段，后端可采用简化策略：

- 登录成功后，统一授予全部功能访问权
- 不做细粒度角色隔离

### 12.3 后续扩展能力

后续如果启用 RBAC，可直接基于 `M5` 扩展：

- 菜单权限
- 页面权限
- API 权限
- AI 工具权限
- 数据范围权限

### 13.2 前端结构建议

### 13.4 页面生成方式

页面不完全手写，应尽量结合：

- 后端返回的页面元数据
- `m9-contract-ui-model.yaml`
- M1/M2/M4 的字段与行为定义

生成或装配页面组件。

### 13.5 图表规范

图表库固定采用 `ECharts`。

图表类型至少支持：

- 柱状图
- 折线图
- 饼图
- 表格型统计卡片

### 14.2 使用方式

1. `message_start`
2. `delta`
3. `tool_call`
4. `tool_result`
5. `render_payload`
6. `message_end`

### 14.3 前端处理方式

前端 AI 对话区应支持：

1. 增量文本拼接
2. 工具调用状态展示
3. 最终结果切换成结构化渲染

例如：

- 文本逐字流出
- 工具调用期间显示“正在查询合同数据”
- 最终自动渲染为表格或图表

## 17. 生成导向要求

该架构文档需要服务于后续 AI 自动生成程序，因此生成时必须遵循以下原则：

1. 优先生成可运行单体，而不是过度拆分微服务。
2. 优先保证本体模型与代码的一一映射关系。
3. 优先复用统一 API 与统一语义注册表。
4. 固定页面与 AI 对话能力必须共用同一后端能力层。
5. 所有 AI 动态查询必须经过只读安全控制。
6. 对于暂未建模的业务能力，AI 可解释，但不得擅自执行写操作。

## 19. 关键结论

本系统的核心不是某个技术框架，而是“本体模型 + 运行时语义注册表 + 可复用 API + AI 工具调用”的统一闭环。

最终落地形态应满足：

1. 本体模型能生成固定业务 UI。
2. 本体模型能生成后端 API。
3. 本体模型能为 AI 提供运行时知识语义。
4. AI 对话能优先复用现有业务能力。
5. 当没有 API 能力时，AI 只能通过严格只读 SQL 查询补位。
6. 固定页面和 AI 动态界面共享同一设计系统和同一业务能力层。

这套架构既适合当前合同管理场景，也适合作为后续更多业务域扩展的通用 AI 原生应用底座。
