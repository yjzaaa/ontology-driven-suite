## 一、本体模型总览

### Q：为什么供应链 ATP/APS 场景需要本体模型？

**A：** 传统 APS 系统将业务逻辑硬编码为规则，当规则边界被突破时系统无法处理。引入 AI 大模型后，模型需要"理解"供应链业务语义，而不只是处理数据字段——"产能"不只是一个数字，它有时间维度、柔性边界和依赖关系；"交期"不只是一个日期，它有优先级含义和合同约束。

本体模型的作用是为 AI 建立一张**业务语义地图**：定义哪些实体存在、实体之间有哪些关系、这些关系遵循哪些约束规则。有了这张地图，AI 推理时才能做到"知其然也知其所以然"，而不是凭借数据字段的统计规律盲目推测。

### Q：本方案的本体模型覆盖哪四个业务域？

**A：** 本体模型以**客户订单（CustomerOrder）**为中心枢纽，向四个方向扩展：

```
需求域（Demand）
    客户 → 客户订单 ← 成品物料
              ↓               ↓
生产域（Production）    供应域（Supply）
    工作中心              库存
    生产工单              BOM层级
    工序                  供应商
              ↓
计划域（Planning）
    工艺路线 → 交期承诺
```

| 业务域 | 核心问题 | 包含实体 |
|-------|---------|---------|
| **需求域** | 谁要什么、要多少、什么时候要 | 客户、客户订单、成品物料 |
| **生产域** | 用什么资源、怎么生产、当前状态如何 | 工作中心、生产工单、工序 |
| **供应域** | 物料从哪来、有多少、能用多少 | 库存、BOM层级、供应商 |
| **计划域** | 能在什么时候做完、怎么做最优 | 工艺路线、交期承诺 |

### Q：本体模型与数据库表的区别是什么？

**A：** 这是一个关键区分：

| 维度 | 数据库表 | 本体模型 |
|-----|---------|---------|
| **目的** | 存储数据，支持查询 | 定义语义，支持推理 |
| **关系表达** | 外键关联，无语义含义 | 命名关系，有业务含义 |
| **约束类型** | 数据完整性约束 | 业务语义约束 |
| **推理能力** | 无 | 可派生新知识（如"因为X，所以Y"） |
| **使用者** | 应用程序 | AI 推理引擎 + 人类 |

举例：数据库中`order.work_center_id = wc.id`只表示关联；本体中`ProductionOrder 在 WorkCenter 上执行`表达了"执行"这一业务语义，AI 由此知道：工作中心产能不足时，该工单无法如期完成。

### Q：本体模型共定义了多少个核心实体对象？

**A：** 共定义 **10 个核心实体对象**，分布在四个业务域：

| 序号 | 实体标识 | 中文名称 | 所属域 |
|-----|---------|---------|-------|
| 1 | `Customer` | 客户 | 需求域 |
| 2 | `CustomerOrder` | 客户订单 | 需求域 |
| 3 | `FinishedItem` | 成品物料 | 需求域 |
| 4 | `WorkCenter` | 工作中心 | 生产域 |
| 5 | `ProductionOrder` | 生产工单 | 生产域 |
| 6 | `Operation` | 工序 | 生产域 |
| 7 | `Inventory` | 库存 | 供应域 |
| 8 | `BOMLevel` | BOM层级 | 供应域 |
| 9 | `Supplier` | 供应商 | 供应域 |
| 10 | `Routing` | 工艺路线 | 计划域 |
| 11 | `ATPCommitment` | 交期承诺 | 计划域 |

> 注：`ATPCommitment` 是本方案新增的核心实体，传统 ERP 中通常只是订单的一个字段，本体中将其独立为实体，使每次承诺可被追溯、对比和学习。

## 二、需求域本体对象

### Q：`Customer`（客户）实体包含哪些属性？为什么这些属性对 AI 推理重要？

**A：**

```
Customer（客户）
├── customer_id          : String       -- 客户唯一标识
├── customer_name        : String       -- 客户名称
├── priority_level       : Enum         -- 战略等级：VIP / Key / Standard / Trial
├── credit_limit         : Decimal      -- 信用额度
├── contract_terms       : ContractRule -- 合同条款集合（见下）
│   ├── penalty_threshold_days : Int    -- 延误超过N天触发罚款
│   ├── penalty_rate     : Decimal      -- 罚款比率（占订单金额%）
│   ├── max_penalty_cap  : Decimal      -- 最高罚款上限
│   └── force_majeure_clause : Boolean  -- 是否含不可抗力条款
├── delivery_reliability : Decimal      -- 历史交期履约率（0-1）
├── complaint_sensitivity: Enum         -- 投诉敏感度：High / Medium / Low
└── account_manager      : String       -- 客户经理（用于升级通知）
```

**对 AI 推理的重要性：**

- `priority_level` 直接影响多订单冲突时的优先级排序逻辑；VIP 客户订单不可轻易延误，这是无法通过数值计算得出的业务判断
- `contract_terms.penalty_threshold_days` 让 AI 知道延误几天会触发实质性经济损失，从而在方案权衡时给予合理权重
- `delivery_reliability` 是评估客户容忍度的历史依据——可靠性高的客户一旦遭遇延误，投诉概率更高
- `complaint_sensitivity` 让 AI 在生成解释时能够表达"此客户对延误敏感，建议主动提前沟通"这类业务建议

### Q：`CustomerOrder`（客户订单）是本体的中心枢纽，它的属性和状态机如何设计？

**A：**

```
CustomerOrder（客户订单）
├── order_id             : String       -- 订单唯一标识（SAP SO号）
├── customer_ref         : → Customer  -- 关联客户
├── item_ref             : → FinishedItem -- 关联成品物料
├── quantity             : Decimal      -- 需求数量
├── unit                 : String       -- 单位（PCS/KG/SET）
├── requested_date       : Date         -- 客户要求交期
├── committed_date       : Date         -- 系统承诺交期（最新一次）
├── order_priority       : Int          -- 当前排程优先级（1最高）
├── order_type           : Enum         -- 订单类型：Standard / Rush / Frame / Sample
├── special_requirements : String[]     -- 特殊要求（包装/认证/分批）
├── status               : OrderStatus  -- 当前状态（见状态机）
└── created_at           : DateTime     -- 下单时间
```

**订单状态机：**

```
[新建] → [已确认] → [生产中] → [完工] → [发货] → [关闭]
              ↓                    ↑
           [暂挂]  ←──────────────── （生产暂停时回退）
              ↓
           [取消]
```

状态机对 AI 推理的意义：AI 在评估 ATP 时需要知道某工单是"已确认"还是"暂挂"，因为暂挂状态的工单产能占用应被视为"潜在释放"，可以参与资源重新分配计算。

### Q：`FinishedItem`（成品物料）的关键属性是什么？与 BOM 的关系如何体现？

**A：**

```
FinishedItem（成品物料）
├── item_id              : String       -- 物料号
├── item_description     : String       -- 物料描述
├── item_category        : Enum         -- 物料类别：MTS（备货）/ MTO（按单生产）/ ATO（按单装配）
├── safety_stock         : Decimal      -- 安全库存水位
├── min_order_quantity   : Decimal      -- 最小生产批量
├── lot_size_rule        : Enum         -- 批量规则：Fixed / EconomicOrderQty / Multiples
├── shelf_life_days      : Int          -- 保质期（天），0表示无限制
├── bom_ref              : → BOMLevel[] -- 关联BOM层级（可能有多版本BOM）
├── routing_ref          : → Routing[]  -- 关联工艺路线（可能有替代路线）
└── abc_classification   : Enum         -- ABC分类：A（高价值）/ B / C（低价值）
```

**`item_category` 对 ATP 推理至关重要：**

- `MTS`（Make-to-Stock）：可以直接从库存承诺，ATP 计算优先查库存
- `MTO`（Make-to-Order）：必须触发生产工单，ATP 计算需要完整的工序链分析
- `ATO`（Assemble-to-Order）：半成品备库，接单后组装，ATP 计算关注装配产能和配件可用性

## 三、生产域本体对象

### Q：`WorkCenter`（工作中心）如何建模才能支持 AI 的产能推理？

**A：** 工作中心是产能约束的核心载体，其建模需要超越"一个数字"：

```
WorkCenter（工作中心）
├── wc_id                : String       -- 工作中心标识
├── wc_name              : String       -- 名称（如：SMT贴片线3号）
├── wc_type              : Enum         -- 类型：Machine / Labor / Mixed
├── plant_id             : String       -- 所属工厂
├── capacity_model       : CapacityDef  -- 产能模型（核心，见下）
│   ├── shifts           : ShiftDef[]   -- 班次配置
│   │   ├── shift_name   : String       -- 班次名（早班/中班/夜班）
│   │   ├── start_time   : Time
│   │   ├── end_time     : Time
│   │   └── available_days : WeekDay[]  -- 工作日配置
│   ├── standard_capacity: Decimal      -- 标准产能（件/小时 或 小时/天）
│   ├── efficiency_factor: Decimal      -- 实际效率系数（0.6-1.0，含等待/换模损耗）
│   ├── overtime_capacity: Decimal      -- 加班最大产能（需审批）
│   └── overtime_cost_rate: Decimal     -- 加班单位成本
├── setup_matrix         : SetupTime[][] -- 换模时间矩阵（不同产品间的换模耗时）
├── maintenance_schedule : MaintenancePlan[] -- 计划性维护窗口
├── bottleneck_flag      : Boolean      -- 是否为识别出的系统瓶颈
└── utilization_target   : Decimal      -- 目标利用率（超出时触发预警）
```

**`setup_matrix`（换模时间矩阵）的重要性：**

换模时间是传统 APS 经常低估的约束。例如从产品 A 切换到产品 B 需要 4 小时，但 B 切换到 A 只需 1 小时——这是非对称约束，必须在本体中建模为矩阵而非单一字段。AI 在排产推理时需要知道当前工作中心上一个产品是什么，才能准确估算换模损耗。

### Q：`ProductionOrder`（生产工单）如何捕捉"计划 vs 实际"的状态偏差？

**A：**

```
ProductionOrder（生产工单）
├── wo_id                : String       -- 工单号（SAP PP订单号）
├── order_ref            : → CustomerOrder -- 关联来源订单（可为空，代表预测性工单）
├── item_ref             : → FinishedItem  -- 生产物料
├── planned_quantity     : Decimal      -- 计划数量
├── confirmed_quantity   : Decimal      -- 已确认（完工）数量
├── scrap_quantity       : Decimal      -- 报废数量
├── planned_start        : DateTime     -- 计划开工时间
├── planned_end          : DateTime     -- 计划完工时间
├── actual_start         : DateTime     -- 实际开工时间（MES）
├── actual_end           : DateTime     -- 实际完工时间（MES，完工后填入）
├── forecast_end         : DateTime     -- AI预测完工时间（ML模型计算）
├── priority             : Int          -- 排程优先级
├── status               : WOStatus     -- 工单状态
├── delay_risk_score     : Decimal      -- 延误风险评分（0-1，ML计算）
├── operations           : → Operation[] -- 包含的工序列表
└── bom_snapshot         : BOMSnapshot  -- 工单创建时的BOM快照（防止BOM变更影响在制工单）
```

**`forecast_end` 与 `planned_end` 的区别：**

这是本体模型的关键设计点。`planned_end` 是 ERP 系统基于标准工时计算的理论完工时间；`forecast_end` 是 ML 模型结合当前实际进度、历史偏差、当前设备状态预测的实际完工时间。两者的差值（`forecast_end - planned_end`）是 ATP 置信度计算的核心输入。当差值为负（预计提前完工），置信度提升；差值为正（预计延误），置信度下降。

### Q：`Operation`（工序）如何建模以支持精确的关键路径计算？

**A：**

```
Operation（工序）
├── op_id                : String       -- 工序标识
├── op_sequence          : Int          -- 工序序号（10, 20, 30...步进设计，便于插入）
├── op_description       : String       -- 工序描述
├── wo_ref               : → ProductionOrder -- 所属工单
├── wc_ref               : → WorkCenter    -- 执行工作中心
├── time_model           : TimeModel    -- 时间模型（核心）
│   ├── setup_time       : Decimal      -- 准备时间（小时）
│   ├── processing_time  : Decimal      -- 加工时间（小时/件）
│   ├── queue_time       : Decimal      -- 等待时间（标准值，实际受负荷影响）
│   ├── move_time        : Decimal      -- 转移时间（工序间物流）
│   └── total_lead_time  : Decimal      -- 总提前期（上述之和）
├── actual_setup_time    : Decimal      -- 实际准备时间（MES记录）
├── actual_processing_time: Decimal     -- 实际加工时间（MES记录）
├── predecessor_ops      : → Operation[] -- 前置工序列表（支持多前置）
├── parallel_flag        : Boolean      -- 是否可与前序工序并行
├── status               : OpStatus     -- 工序状态：Planned/InProgress/Completed/Skipped
├── completion_percentage: Decimal      -- 完成百分比（0-100，MES实时）
└── quality_hold_flag    : Boolean      -- 是否因质量问题暂停
```

**关键路径计算：**

`predecessor_ops` 定义了工序间的依赖关系（有向无环图），ATP 系统基于此计算关键路径（Critical Path）——即决定整个工单完工时间的最长工序链。AI 在推理时重点关注关键路径上的工序产能，而非平均所有工序的资源压力。

## 四、供应域本体对象

### Q：`Inventory`（库存）为什么需要区分四种数量而不是一个总数？

**A：**

```
Inventory（库存）
├── inventory_id         : String
├── item_ref             : → FinishedItem / ComponentItem
├── plant_id             : String       -- 所在工厂
├── storage_location     : String       -- 库位
├── quantity_model       : QuantityModel -- 四维数量模型（核心）
│   ├── on_hand_qty      : Decimal      -- 现货库存（实际在库，可立即使用）
│   ├── in_transit_qty   : Decimal      -- 在途数量（已发货/采购，未到库）
│   ├── reserved_qty     : Decimal      -- 已预留数量（被其他订单锁定，不可再用）
│   └── available_qty    : Decimal      -- 可用数量 = on_hand + in_transit - reserved
├── in_transit_details   : InTransitItem[] -- 在途明细（预计到货日期）
│   ├── po_id            : String       -- 采购订单号
│   ├── expected_arrival : Date         -- 预计到货日
│   └── quantity         : Decimal
├── reorder_point        : Decimal      -- 再订货点
├── last_updated         : DateTime     -- 最后更新时间（数据时效性标注）
└── data_source          : Enum         -- 数据来源：SAP_LIVE / SAP_SNAPSHOT / MES_ADJUSTED
```

**四维数量的 ATP 推理意义：**

- AI 评估 ATP 时必须使用 `available_qty`，而非 `on_hand_qty`——已被其他订单预留的库存不能重复承诺
- `in_transit_details` 让 AI 能够做"未来库存可用性"推理：如果在途物料在需求日期前到货，可以纳入可用资源
- `data_source` 标注数据时效性，AI 在生成解释时应提示"库存数据来自X小时前的快照，建议人工确认"

### Q：`BOMLevel`（BOM层级）如何建模以支持多层 BOM 展开和替代料推理？

**A：**

```
BOMLevel（BOM层级）
├── bom_id               : String       -- BOM记录标识
├── bom_version          : String       -- BOM版本号（支持多版本共存）
├── parent_item          : → FinishedItem / ComponentItem -- 父项物料
├── child_item           : → ComponentItem -- 子项物料
├── level                : Int          -- BOM层级（0=成品，1=一级组件，2=原材料）
├── quantity_per         : Decimal      -- 单位父项需用量
├── scrap_factor         : Decimal      -- 损耗系数（1.05 = 5%损耗）
├── effective_from       : Date         -- 生效日期
├── effective_to         : Date         -- 失效日期（支持ECO工程变更）
├── alternative_items    : AlternativeItem[] -- 替代料清单
│   ├── alt_item_ref     : → ComponentItem
│   ├── usage_priority   : Int          -- 替代使用优先级
│   ├── substitution_ratio: Decimal     -- 替代比例
│   └── approval_status  : Enum        -- 替代批准状态：Approved/Conditional/Pending
├── phantom_flag         : Boolean      -- 是否虚拟件（展开时跳过，不产生工单）
└── purchase_or_make     : Enum         -- 自制/外购：Make / Buy / Either
```

**替代料推理的重要性：**

当某种原材料库存不足时，传统系统只能报"缺料"，而 AI 可以基于 `alternative_items` 推理："主料 A 缺货，但替代料 B 库存充足且已获批准，使用替代料 B 可以将交期从 12 月 22 日提前到 12 月 18 日，建议采购确认后执行。" 这是 AI 超越规则引擎的具体体现。

### Q：`Supplier`（供应商）需要建模哪些属性来支持供应风险推理？

**A：**

```
Supplier（供应商）
├── supplier_id          : String
├── supplier_name        : String
├── supplier_tier        : Enum         -- 供应商层级：Tier1 / Tier2 / Approved / Backup
├── supply_lead_time     : LeadTimeDef  -- 供货提前期
│   ├── standard_lt      : Int          -- 标准提前期（天）
│   ├── rush_lt          : Int          -- 紧急提前期（天，通常附加成本）
│   └── lt_variability   : Decimal      -- 提前期变异系数（越大越不稳定）
├── moq                  : Decimal      -- 最小订购量
├── capacity_limit       : Decimal      -- 供应商产能上限（件/月）
├── delivery_performance : DeliveryKPI  -- 历史交货绩效
│   ├── on_time_rate     : Decimal      -- 准时交货率（近12个月）
│   ├── quality_pass_rate: Decimal      -- 来料合格率
│   └── average_delay_days: Decimal     -- 平均延误天数
├── geo_risk_level       : Enum         -- 地缘风险：Low / Medium / High
├── single_source_flag   : Boolean      -- 是否唯一供应商（单一来源风险标识）
└── active_pos           : → PurchaseOrder[] -- 当前在途采购订单
```

**供应风险推理示例：**

当 `single_source_flag = true` 且 `delivery_performance.on_time_rate < 0.85` 时，AI 应在 ATP 承诺中自动标注"该物料为单一来源供应，供应商历史准时率85%以下，建议在承诺交期中增加5天缓冲"——这类综合判断无法通过简单规则实现，正是 LLM 推理的价值区域。

## 五、计划域本体对象

### Q：`Routing`（工艺路线）如何建模以支持替代路线选择？

**A：**

```
Routing（工艺路线）
├── routing_id           : String       -- 工艺路线标识
├── routing_version      : String       -- 版本号
├── item_ref             : → FinishedItem -- 适用物料
├── routing_type         : Enum         -- 路线类型：Standard / Alternative / Rework
├── total_lead_time      : Decimal      -- 总理论提前期（工序提前期之和）
├── critical_path_ops    : → Operation[] -- 关键路径工序列表
├── bottleneck_wc        : → WorkCenter  -- 当前识别的瓶颈工作中心
├── operations           : → OperationTemplate[] -- 工序模板列表（实例化为工单工序）
│   ├── op_sequence      : Int
│   ├── wc_ref           : → WorkCenter
│   ├── standard_setup   : Decimal
│   └── standard_process : Decimal      -- 每件加工时间
├── alternative_routings : → Routing[]  -- 替代工艺路线
│   └── applicability_condition : String -- 替代路线的使用条件描述
├── min_batch_size       : Decimal      -- 最小经济批量
└── max_batch_size       : Decimal      -- 最大批量（工艺约束）
```

**替代路线在 ATP 中的应用：**

当主工艺路线（Standard）的关键工序产能紧张时，AI 可以评估替代路线（Alternative）的可行性。例如主路线经过 SMT 贴片线（瓶颈），替代路线使用手工贴片，工时增加 30% 但可绕开瓶颈——AI 需要基于本体信息做这个权衡，而不是只报告"产能不足"。

### Q：`ATPCommitment`（交期承诺）为什么要作为独立实体而不是订单的一个字段？

**A：** 这是本体模型最重要的设计决策之一。将承诺独立为实体，实现了三个关键能力：

```
ATPCommitment（交期承诺）
├── commitment_id        : String       -- 承诺唯一标识
├── order_ref            : → CustomerOrder -- 关联订单
├── commitment_version   : Int          -- 承诺版本（同一订单可有多次承诺历史）
├── committed_date       : Date         -- 承诺交期
├── commitment_type      : Enum         -- 承诺类型：
│                                       --   Standard（标准排程）
│                                       --   Overtime（加班方案）
│                                       --   PrioritySwap（调换优先级）
│                                       --   PartialDelivery（分批交付）
│                                       --   AlternativeRouting（替代工艺）
├── confidence_score     : Decimal      -- 置信度（0-100，ML计算）
├── risk_level           : Enum         -- 风险等级：High / Medium / Low
├── reason_chain         : String[]     -- 推理原因链（AI生成，可解释）
├── cost_impact          : Decimal      -- 与标准方案相比的额外成本
├── data_snapshot        : DataSnapshot -- 承诺时刻的关键数据快照
│   ├── capacity_snapshot: ...          -- 产能状态快照
│   ├── inventory_snapshot: ...         -- 库存状态快照
│   └── competing_orders : String[]     -- 竞争资源的订单列表
├── created_by           : Enum         -- 承诺来源：AI_AUTO / HUMAN_CONFIRMED / HUMAN_OVERRIDE
├── created_at           : DateTime     -- 承诺时间
├── actual_delivery_date : Date         -- 实际交货日期（事后填入，用于反馈学习）
└── deviation_days       : Int          -- 实际偏差天数（actual - committed，负=提前，正=延误）
```

**独立实体的三个关键价值：**

1. **历史追溯：** 同一订单可能经历多次承诺修改，每次修改都有完整记录，支持"为什么承诺从15日改到18日"的审计追溯
2. **反馈学习：** `actual_delivery_date` 和 `deviation_days` 是 ML 模型和向量库的训练数据来源；没有独立实体就无法系统性积累这些数据
3. **模式识别：** 通过分析历史 `ATPCommitment` 的 `commitment_type` 分布，可以发现"每逢月末加班方案使用率上升"等规律，为产能规划提供依据

### Q：本体模型定义了哪些核心关系？每种关系的语义是什么？

| `executed_at` | Operation | WorkCenter | 工序在工作中心执行 | N:1 |
| `precedes` | Operation | Operation | 工序先后依赖关系 | N:N |

#### 供应域关系

### Q：`precedes`（工序先后依赖）关系有哪些特殊情况需要建模？

**A：** 工序依赖不是简单的线性链条，存在四种拓扑结构：

**结构1：线性链（最常见）**
```
工序10（备料）→ 工序20（加工）→ 工序30（检验）→ 工序40（包装）
```

**结构2：并行工序（可同时进行）**
```
工序10（主体加工）→ 工序30（总装）
工序20（配件加工）→ 工序30（总装）
工序10 和 工序20 可并行，30依赖10和20都完成
```
建模方式：`工序30.predecessor_ops = [工序10, 工序20]`，`parallel_flag = true`

**结构3：部分完工触发（overlap）**
```
工序10完成50%后，工序20可以开始（流水作业）
```
建模方式：增加 `overlap_percentage: Decimal` 属性，表示前序完成多少比例后后续可启动

**结构4：跨工单依赖（装配场景）**
```
半成品工单A的完工 → 触发 总装工单B的工序10开始
```
建模方式：`precedes` 关系可跨工单，`ProductionOrder.predecessor_orders: → ProductionOrder[]`

## 七、核心行为规则建模

### Q：什么是"行为规则建模"？与属性定义有什么区别？

**A：** 属性定义描述实体"是什么"，行为规则建模描述实体"能做什么"和"在什么条件下如何响应"。行为规则是 AI 推理时的决策依据，直接影响 ATP 承诺的质量。

本体模型中的行为规则分为三类：
- **计算规则（Calculation Rules）：** 如何从已有属性派生出新值
- **触发规则（Trigger Rules）：** 满足什么条件时执行什么动作
- **约束规则（Constraint Rules）：** 什么条件下某个操作不被允许

### Q：产能计算的行为规则如何建模？

**A：**

**规则 C-01：工作中心日可用产能计算**

```
WorkCenter.daily_available_capacity = 
    SUM(shift.duration for shift in active_shifts) 
    × standard_capacity 
    × efficiency_factor 
    - scheduled_maintenance_hours
    - [overtime_capacity if overtime_approved else 0]
```

注：`efficiency_factor` 通常取 0.75-0.85（含换模、等待等损耗），而非理论上的 1.0。AI 推理时应使用此值而非标准产能，否则会系统性高估产能。

**规则 C-02：工序实际占用时间计算**

```
Operation.actual_duration = 
    setup_time（含换模时间，从 WorkCenter.setup_matrix 查询）
    + processing_time × quantity 
    + queue_time（动态值，随负荷变化：负荷>85%时 queue_time 系数×1.5）
    + move_time
```

**规则 C-03：生产工单最早完工时间（关键路径法）**

```
对工单的所有工序，按 precedes 关系构建有向无环图（DAG）
对每个工序节点计算：
    earliest_start(op) = MAX(earliest_end(predecessor) for predecessor in op.predecessor_ops)
    earliest_end(op) = earliest_start(op) + op.actual_duration / WorkCenter.daily_available_capacity
ProductionOrder.earliest_completion = MAX(earliest_end(op) for op in critical_path_ops)
```

### Q：优先级冲突的触发规则如何建模？

**A：**

**规则 T-01：产能超负荷触发重排（Capacity Overload Trigger）**

```
IF WorkCenter.current_load > WorkCenter.daily_available_capacity * 1.0 THEN
    trigger: CapacityConflictEvent
    affected_orders: [所有在该工作中心排程的订单，按 order_priority 排序]
    resolution_options:
        - 低优先级订单顺延
        - 启用加班产能（需审批）
        - 启用替代工作中心（如有）
        - 外协加工（如供应商有能力）
```

**规则 T-02：VIP 客户订单保护规则**

```
IF CustomerOrder.customer.priority_level = 'VIP'
AND CustomerOrder.status IN ['已确认', '生产中']
AND ATPCommitment.risk_level = 'High'
THEN
    trigger: VIPOrderAlert
    actions:
        - 锁定该订单的产能资源（不可被其他订单抢占）
        - 通知客户经理
        - 要求人工审核任何影响该订单的排产调整
```

**规则 T-03：承诺交期风险预警**

```
IF (ProductionOrder.forecast_end - CustomerOrder.committed_date) > 3 days
THEN
    trigger: DeliveryRiskAlert
    risk_level: 
        1-3天延误 → Medium
        3-7天延误 → High
        >7天延误  → Critical
    actions:
        - 更新 ATPCommitment.risk_level
        - 触发新一轮 ATP 重新评估
        - 置信度降级处理
```

### Q：库存可用性的约束规则如何建模？

**A：**

**规则 CR-01：库存不可重复承诺**

```
Inventory.available_qty = on_hand_qty + in_transit_qty - reserved_qty

CONSTRAINT: 
    对任何新的 CustomerOrder 承诺，
    SUM(reserved_qty for all committed orders) 不得超过 
    on_hand_qty + SUM(in_transit_qty where expected_arrival <= committed_date)
```

**规则 CR-02：在途库存时效约束**

```
仅当 InTransitItem.expected_arrival <= CustomerOrder.committed_date - safety_buffer_days
时，该在途数量才可计入 ATP 可用资源。
safety_buffer_days 默认值 = 2（考虑到货检验时间）
```

**规则 CR-03：替代料使用约束**

```
BOMLevel.alternative_items 中的替代料，仅当满足以下全部条件时可使用：
    1. alt_item.approval_status = 'Approved'（或 'Conditional' 且当前场景满足条件）
    2. alt_item 的 Inventory.available_qty >= required_quantity * substitution_ratio
    3. 使用替代料不影响产品质量认证（需查询认证数据库）
    4. 客户合同未明确禁止使用替代料
```

## 八、约束语义建模

### Q：供应链约束的语义分类有哪些？

**A：** 约束不是单一类型，按来源和性质分为五类，每类对 AI 推理的影响方式不同：

| 约束类型 | 来源 | 是否可突破 | AI 处理方式 |
|---------|------|-----------|------------|
| **硬约束（Hard）** | 物理/法规限制 | 不可突破 | 直接排除违反的方案 |
| **软约束（Soft）** | 业务偏好/成本 | 可突破但有代价 | 计算突破代价，纳入方案对比 |
| **时间约束** | 工艺/合同要求 | 部分可调整 | 关键路径分析 |
| **资源约束** | 产能/库存限制 | 可通过加班/采购放松 | 资源负荷平衡 |
| **优先级约束** | 客户战略/合同 | 动态调整 | 多目标优化权衡 |

### Q：各类约束的具体建模示例是什么？

**A：**

**硬约束示例：**

```
Constraint HC-01（工序不可跳过）：
    对于 Operation where skip_allowed = false，
    不得在生产工单中省略该工序（如质检工序）

Constraint HC-02（物料保质期）：
    FinishedItem.shelf_life_days > 0 时，
    ATPCommitment.committed_date + delivery_transit_days 
    <= production_date + shelf_life_days
    否则该承诺方案无效

Constraint HC-03（MOQ限制）：
    生产工单的 planned_quantity >= FinishedItem.min_order_quantity
    不允许生产低于最小批量的订单（除非特批）
```

**软约束示例（带代价函数）：**

```
Constraint SC-01（加班成本）：
    使用 WorkCenter.overtime_capacity 时，
    cost_penalty += overtime_hours × WorkCenter.overtime_cost_rate
    优先级：在满足交期的前提下，最小化 cost_penalty

Constraint SC-02（优先级降级代价）：
    将 CustomerOrder.order_priority 降低1级时，
    risk_penalty += customer.priority_level_weight × delay_days
    VIP客户的 priority_level_weight = 10
    Standard客户的 priority_level_weight = 1
```

### Q：提前期（Lead Time）的非线性特性如何建模？

**A：** 这是供应链建模中最常被简化处理的问题，也是 AI 推理准确性的关键。

**传统建模（错误简化）：**
```
lead_time = constant（一个固定天数）
```

**本体模型的非线性建模：**

```
LeadTimeModel（提前期模型）
├── base_lead_time       : Decimal      -- 基础提前期（低负荷，<70%利用率）
├── load_adjustment      : LoadCurve    -- 负荷调整曲线
│   ├── [0%, 70%]        → factor = 1.0（标准）
│   ├── [70%, 85%]       → factor = 1.2（轻度拥堵，排队时间增加）
│   ├── [85%, 95%]       → factor = 1.5（中度拥堵）
│   └── [95%, 100%+]     → factor = 2.0+（严重拥堵，非线性急剧增加）
├── quantity_adjustment  : QuantityCurve -- 数量调整（大批量分批生产）
│   └── large_batch_threshold: Decimal  -- 超过此数量，提前期非线性增加
└── historical_deviation : DistributionDef -- 历史偏差分布
    ├── mean_deviation   : Decimal      -- 平均偏差天数
    ├── std_deviation    : Decimal      -- 标准差
    └── p90_deviation    : Decimal      -- 90%分位偏差（保守承诺时使用）
```

AI 推理时：标准承诺使用 `mean_deviation` 修正，保守承诺（VIP客户、罚款风险高）使用 `p90_deviation` 修正。

## 九、事件语义建模

### Q：本体模型如何对供应链中的"事件"进行语义建模？

**A：** 事件建模是本体论的重要组成部分，定义了什么事情发生后会触发什么变化，是 AI 实时响应能力的基础。

```
SupplyChainEvent（供应链事件基类）
├── event_id             : String
├── event_type           : EventType    -- 事件类型（见下分类）
├── event_source         : Enum         -- 来源：SAP / MES / Manual / AI
├── occurred_at          : DateTime
├── affected_entities    : Entity[]     -- 受影响的实体列表
├── severity             : Enum         -- 严重程度：Info / Warning / Critical
└── resolution_required  : Boolean      -- 是否需要人工干预
```

**事件类型分类：**

| 事件类型 | 触发源 | 影响范围 | AI响应行动 |
|---------|-------|---------|----------|
| `DemandChange`（需求变更） | 客户/销售 | 相关订单及其工单 | 重新评估受影响订单的 ATP |
| `CapacityOverload`（产能超负荷） | 优化引擎计算 | 工作中心及排程订单 | 生成优先级重排建议 |
| `MaterialShortage`（物料短缺） | 库存监控 | 相关工单及订单 | 触发采购建议或替代料评估 |
| `OperationDelay`（工序延误） | MES实时数据 | 下游工序及交期承诺 | 更新预测完工时间，评估承诺风险 |
| `EquipmentFailure`（设备故障） | MES告警 | 工作中心产能 | 紧急重排，评估外协可行性 |
| `SupplierDelay`（供应商延误） | 采购更新 | 在途物料及相关工单 | 更新库存预测，评估替代供应 |
| `QualityHold`（质量暂停） | MES/质量系统 | 在制工单 | 计算质量暂停影响的交期变化 |
| `PriorityEscalation`（优先级升级） | 客户/管理层 | 目标订单及竞争订单 | 重新排程，评估对其他订单影响 |

### Q：`DemandChange`（需求变更）事件的完整处理流程如何建模？

**A：** 这是 ATP 场景最核心的事件，完整语义建模如下：

```
DemandChange Event（需求变更事件）
├── change_type          : Enum
│   ├── DateAcceleration  -- 要求提前交期（最频繁）
│   ├── DateDelay        -- 要求延后交期
│   ├── QuantityIncrease -- 增量
│   ├── QuantityDecrease -- 减量
│   └── OrderCancellation -- 取消订单
├── original_value       : Value        -- 变更前值
├── requested_value      : Value        -- 变更后值
├── change_delta         : Value        -- 变化量（如：提前7天）
└── business_reason      : String       -- 变更原因（客户填写）
```

**AI 处理链（DateAcceleration 场景）：**

```
Step 1 - 影响范围识别：
    从 CustomerOrder 出发，通过 triggers 关系找到所有关联 ProductionOrder
    通过 contains 关系找到所有 Operation
    通过 executed_at 关系找到所有占用的 WorkCenter
    通过 bom_ref 关系找到所有需要的物料及其 Inventory

Step 2 - 资源竞争分析：
    对每个 WorkCenter，查找在新目标交期范围内的所有其他 CustomerOrder
    按 order_priority 排序，识别资源竞争关系

Step 3 - 可行方案枚举：
    方案A：标准排程下最早完工时间
    方案B：启用加班产能后最早完工时间
    方案C：调整竞争订单优先级后最早完工时间
    方案D：启用替代工艺路线后最早完工时间

Step 4 - AI 推理与权衡：
    基于 Customer.contract_terms、竞争订单的 Customer.priority_level、
    历史相似 DemandChange 的 ATPCommitment.deviation_days
    推荐最优方案并生成 reason_chain

Step 5 - 承诺写入：
    创建新版本 ATPCommitment
    快照当前关键数据状态
    更新 CustomerOrder.committed_date
```

| `planned_end` | AFKO.GLTRP | 计划完工日期 |
| `status` | AFKO.FEVOR（+状态码） | 工单状态 |
| `planned_quantity` | AFKO.GAMNG | 工单数量 |

**`Operation` ↔ MES 实时工序数据**

| 本体属性 | MES 字段 | 说明 |
|---------|---------|------|
| `actual_start` | OPERATION.ACTUAL_START | 实际开工（秒级精度） |
| `completion_percentage` | OPERATION.COMPLETION_PCT | 完成百分比 |
| `actual_processing_time` | OPERATION.ACTUAL_PROC_TIME | 实际加工时间 |
| `quality_hold_flag` | OPERATION.ON_HOLD | 质量暂停标志 |

**数据对齐问题处理：**

SAP 计划数据（天级精度）与 MES 实际数据（分钟级精度）之间存在时间粒度不一致的问题。本体层通过以下规则处理：

```
DataAlignment Rule：
    当 MES.actual_start 与 SAP.planned_start 偏差 > 4小时 时，
    以 MES 实际数据为准更新本体状态，
    并生成 OperationDelay 事件（如实际晚于计划）
    或 OperationAcceleration 事件（如实际早于计划）
```

## 十一、本体演进策略

### Q：本体模型应该如何随业务发展而演进？

**A：** 本体不是一次性设计完成的产物，而是持续演进的业务知识积累。遵循以下策略：

**阶段一：最小可用本体（MVP，对应实施第一阶段）**

优先建立 ATP 承诺场景必需的实体和关系：
- 需求域：`Customer`（简化属性）、`CustomerOrder`、`FinishedItem`
- 生产域：`WorkCenter`（基础产能模型）、`ProductionOrder`、`Operation`（线性依赖）
- 计划域：`ATPCommitment`
- 暂缓建立：`BOMLevel`多层展开、替代料、替代路线

**阶段二：能力增强本体（对应实施第二阶段）**

在 MVP 验证后扩展：
- 供应域完整建模（`Inventory`四维数量、`BOMLevel`替代料、`Supplier`绩效）
- 工序并行和部分完工触发规则
- 事件语义建模（`DemandChange`、`CapacityOverload`）
- 提前期非线性模型

**阶段三：完整本体（对应实施第三阶段）**

- 多工厂本体扩展（跨厂实体关系、物流网络节点）
- APS 排产场景所需约束规则
- 跨企业边界（供应商端数据集成）

**版本管理原则：**

```
本体版本变更分级：
    Minor变更（新增属性、新增实体）：
        → 向前兼容，AI Prompt 中的上下文构建模块自动适配
    Major变更（修改关系语义、删除实体）：
        → 需要同步更新 Prompt 模板和校验规则
        → 历史 ATPCommitment 数据保持旧版本快照不变
```

### Q：如何评估本体模型的质量和完整度？

**A：** 从三个维度评估：

**覆盖度（Coverage）：** ATP/APS 场景中涉及的业务概念，有多少比例在本体中有对应的实体或关系。目标：核心场景的概念覆盖度 > 90%。

**一致性（Consistency）：** 本体中的规则定义是否存在矛盾。评估方法：随机抽取 50 个历史 ATP 场景，用本体规则推演，验证推演结果是否与实际决策一致。

**实用性（Utility）：** 本体对 AI 推理质量的实际提升。量化方式：对比"使用本体语义上下文"和"不使用本体"的两组 LLM 推理结果，计算承诺准确率差异。
